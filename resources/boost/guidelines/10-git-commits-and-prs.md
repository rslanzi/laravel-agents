# Git: Commits and Pull Requests

## Authorship: the work is the developer's

Commits and pull requests are authored by the developer who runs the agent, never by the agent.

- Use the git identity already configured on the machine. Never run `git config user.name` / `user.email`, never pass `--author`.
- Do **not** add `Co-Authored-By:` trailers, "Generated with ..." / "Generated by ..." footers, agent names, model names, session links or emoji signatures to commit messages, PR titles, PR descriptions, code comments or review comments.
- Do not mention the agent in changelogs, ADRs or documentation as an author.
- Commit, push or open a PR only when the user asked for it.

## Commits: Conventional Commits

Format: `type(scope): subject`

- **type**: `feat`, `fix`, `refactor`, `test`, `docs`, `perf`, `build`, `ci`, `chore`, `revert`. Use `feat!` / `fix!` or a `BREAKING CHANGE:` footer for breaking changes.
- **scope**: the bounded context in kebab-case (`booking`, `billing`), or `deps`, `ci`, `arch` for cross-cutting changes.
- **subject**: imperative, lower case, no final period, max ~72 characters: `feat(booking): allow staff to override overlapping appointments`.
- **body** (optional): why the change was made and what it affects, wrapped at 72 columns. Reference the ADR (`Refs: ADR-0007`) and the issue (`Closes #123`).
- One logical change per commit. Tests go in the same commit as the code they cover. Formatting-only or Rector-only changes go in a separate `style:`/`refactor:` commit when they touch unrelated files.
- Never commit generated files, `.env`, `vendor/`, `node_modules/`, coverage reports or local tool caches.

## Branches

`type/short-description`, e.g. `feat/booking-overlap-override`, `fix/billing-rounding`. Branch from the default branch, rebase on it before opening the PR, never rewrite history that others have pulled.

## Pull requests

- **Small and focused**: one feature, fix or refactor per PR. Aim for under ~400 changed lines excluding tests and generated files; split larger work into a sequence of PRs (e.g. migration and model first, then Actions, then UI).
- **Title**: same format as a Conventional Commit (it becomes the squash commit message).
- **Description**: fill the repository's PR template (`.github/pull_request_template.md`): what, why, how to test, ADR, checklist. No agent attribution (see above).
- **Green before review**: `composer check` passes locally and CI is green. Do not ask for review on a red PR.
- **Self-review the diff** before opening: no debug code (`dd`, `dump`, `ray`, `logger()` left behind), no commented-out code, no unrelated changes.
- Answer review comments with a fix commit or an explanation; do not resolve threads you did not address.
